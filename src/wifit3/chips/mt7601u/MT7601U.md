# MT7601U

## Captured Wireless Card

- MediaTek MT7601U, 1x1 2.4 GHz 802.11n (b/g/n), 1 TX chain, 1 RX chain.
- `148f:7601` — the tested unit, a generic no-name dongle.
- USB 2.0 high speed, isochronous bulk endpoints, max packet 512 on all of them.
- MAC `20:0d:b0:30:51:59`, EEPROM version 1 (from the cold-boot capture).
- Captures: `driver_captures/captures_mt7601u_{superwang,antenna}/` — `capture-1-coldboot`, `capture-2-coldboot-longwait`, `capture-3-monitor-chan` (kernel driver), `capture-5-port-init` (this port's own bring-up), `capture-6-kernel-tx` (kernel injection). Gitignored; re-capture from the kernel driver or the tools in `scripts/chips/mt7601u/`.

## Linux Driver Source

- Upstream: `drivers/net/wireless/mediatek/mt7601u/` in the Linux tree, mainline.
- Pinned at tag `v7.2`. 23 files, vendored gitignored at `driver_sources/mt7601u-source-v7.2/`.
- Self-contained relative to `mt76/`: only `mt76` helper headers are shared, no `mt76` modules are linked in.

## Python Port Details

- Claims 17 VID:PIDs, one per entry of the kernel's `mt7601u_device_table` (`usb.c:14`). Discovery walks `chips/*/__init__.py` and matches on VID:PID alone — no OUI narrowing, since the table carries none.
- **Status on hardware:** connect, EEPROM, firmware download, register init, BBP/RF calibration, channel tune 1–14, receive, and injection all work. A 4-hop scan yields 373 packets and 5 APs with correct SSID, channel, RSSI and encryption.
- The verify gates (`scripts/chips/mt7601u/`) prove EEPROM read+decode 160/160 ops, firmware download 78/78, WCID/key burst clears 13/13, and 55/55 recorded channel tunes replayed op-for-op — all against the kernel captures, with no hardware attached.
- No shared code with other chip drivers.

**Non-obvious in the port**

- **RX URBs must be submitted between `mcu_cmd_init` and `write_mac_initvals`.** That is where `dma.c:517 mt7601u_dma_init` sits. Armed anywhere earlier the chip never streams a byte; armed at the end of `connect()` it does not either. Measured: 0 buffers armed before `mcu_cmd_init`, 118 buffers armed at that point.
- **`__mt7601u_vendor_single_wr` splits every 32-bit register write into two 16-bit control requests** (`usb.c:157`): low half at `offset`, high half at `offset+2`. In usbmon text the value half is the *first* hex group and the register is the *second*. Any diff of port writes against a capture is meaningless until the halves are reassembled.
- `MT_TXD_INFO_LEN` is `round_up(txwi + frame, 4)` — it excludes the DMA info word and the zero trailer. A capture reads LEN 48 on a 56-byte transfer.
- Injection defaults to `ack=False`. `tx.c` sets `MT_TXWI_ACK_CTL_REQ` only when `IEEE80211_TX_CTL_NO_ACK` is clear, and a broadcast deauth is noack.
- **`MT_TXWI_ACK_CTL_NSEQ` set is what asks the MAC to stamp the sequence number** (`rt2800.h:3097`: "0: Don't assign hw sequence number, 1: Assign"; `tx.c:160` sets it for `IEEE80211_TX_CTL_ASSIGN_SEQ`). An earlier entry here had the polarity inverted and concluded no software stamping was needed, so `_stamp_tx_seq` was a no-op and every frame of a burst went out with `seq_ctrl` 0 for a receiver's duplicate filter to discard. The emitted byte was never wrong -- clear is the kernel's monitor form, and the capture agrees -- but clear means **the MPDU's own seq_ctrl is transmitted**, so the caller has to supply it. `driver.py:_stamp_tx_seq` now does, as `mt76x0u` and `mt76x2u` already did for the identical txwi.
- `MT_USB_DMA_CFG_RX_BULK_AGG_EN` is set only when `transport.in_max_packet == 512`. That value is filled by `assign_pipes()` during `connect()`, long after the driver object exists — read it live, never snapshot it at construction.
- Channel 14 tunes and receives. `iw` refuses it because the nl80211 regdomain for 2.4 GHz excludes 2484 MHz; that is a regdomain restriction, not a silicon one, and this port bypasses nl80211.
- `MT_RX_ORDER` 3 → RX buffers are `PAGE_SIZE << 3` = 32768 bytes.
- TSI/TSSI reads, `rf_rr`, and the `_KICK` poll all mutate device state. Reads are not commutative; keep their order as the captures have it.

## Known Problems

- **WCID allocation is not ported.** `wcid.py` has no `wcid_mask` bookkeeping equivalent to `main.c:191`, and the group WCID from `.add_interface` is never allocated. Monitor TX is unaffected: the kernel sends it on `mon_wcid->idx = 0xff` (`init.c:590`, `tx.c:198`), which this port already matches, and capture-6 reproduced 7680 byte-identical kernel deauths. WCID allocation only matters for client association and AP mode.
- **Key table programming is not ported.** No `MT_KEY_TABLE` writes; hardware decryption is unavailable. PMKID is not reachable by porting this alone: the kernel supports `NL80211_IFTYPE_STATION` (`init.c:612`) and a PMKID arrives in EAPOL M1 *after* association, so it needs a full 802.11 client state machine (auth, assoc, 4-way). `campaigns/auth_assoc.py` sends frames only, with no station machinery.
- **WPS is advertised in the UI but cannot be extracted on this driver.** The scanner log reports "WPS PushButton Extraction is enabled" and the AP table's WPS column is populated from real beacon tags, but WPS requires AP mode, which is unported.
- **AP mode is not ported.** `mt7601u_add_interface` only does MAC-address and group-WCID work upstream, so the gap is the WCID/keys above rather than a missing function.
- **`iw dev ... scan` returns `-EOPNOTSUPP`.** mt7601u has no cfg80211 scan in any driver, kernel or this port. Scanning is channel-hopping.
- **NetworkManager will revert `wlan1` to managed.** Use `nmcli device set <if> managed no` before monitoring. Avoid `airmon-ng check kill` — it drops the machine's internet interface.
- **The kernel `mt7601u` module must never have touched this dongle.** If the kernel driver probes it, the chip is left in a state a userspace cold bring-up cannot recover from, and RX delivers zero bytes with no error at any read timeout. `modprobe -r` does *not* undo the kernel's chip init. Blacklist it (`/etc/modprobe.d/blacklist-mt7601u.conf`) and replug; unloading afterwards is not sufficient.
- **The RX filter is the kernel's monitor value, derived rather than copied.** `init.c:238-244` programs the managed-STA default (`0x00017f97`) inside `mac_start`, and `main.c:116-125` reconfigures it for the interface's flags. The register **drops on set** -- `main.c:107` sets a bit only when mac80211 did *not* ask for that class -- so a monitor, which asks for `FIF_OTHER_BSS`, `FIF_CONTROL` and `FIF_PSPOLL` and not `FIF_FCSFAIL` or `FIF_PLCPFAIL`, clears `PROMISC`, the `main.c:119` control group and `PSPOLL`, and keeps `CRC_ERR`, `PHY_ERR`, `VER_ERR` and `DUP`. `RTS` sits outside that group and stays set. `RX_FILTER_MONITOR` computes to `0x00001093`, the value the kernel itself writes for monitor in the captures.
- **Superseded: the measurement that said `CRC_ERR`/`PHY_ERR` suppress unicast.** An earlier session A/B'd the full managed default against `PROMISC|DUP` and blamed the error bits for catching 250 beacons and zero unicast in 20 s. That A/B isolated no bit: `0x17f97` also sets `PROMISC`, which is what drops other-BSS unicast, plus the whole control group. The C contradicts the attribution, and so does the same session's `0x06` trial -- `CRC_ERR|PHY_ERR` set, which cut the phantom frames to two. Do not restore `PROMISC|DUP` on those numbers.
- **Accepting FCS-failed frames duplicated real APs in the UI.** With `CRC_ERR` clear the MAC delivered frames that failed FCS, and a beacon with a flipped byte in the BSSID or the RSN element registers as a second AP with the same SSID and different encryption. Reported on live hardware against a home router. Two gates now gate it: `CRC_ERR` set in the filter (`main.c:117`) and `MT_RXINFO_CRCERR` tested in `rx.py:decode_segment` (`mac.h:54`).
- **PHY-noise frames mint phantom clients, and a data-subtype gate is the only software fix.** With promiscuous RX on, the silicon also delivers frames whose payload is RF noise: the fc nibble sweeps the subtype field randomly and addr2/addr3 are random bytes, each minting a "client" out of addr2. No `MT_RX_FILTR_CFG` value removes them (`0x06` still passes two), and that session read RXWI as carrying no CRC bit -- it does: `mac.h:54 MT_RXINFO_CRCERR` is bit 8 of `rxinfo`, now tested in `rx.py:decode_segment`. `parser.py:DATA_SUBTYPES` rejects any data frame whose subtype is outside the 12 IEEE 802.11 Table 9-1 values. **Residual, unresolved:** subtypes 8/9 are *in* the table, so long frames (3551/3834 bytes) with random addresses still register. The remaining lever is the sink layer -- require a data-frame client's BSSID to be an AP already learned from a beacon. Do not re-derive the subtype gate; it is measured.
- **PHY-error data frames minted phantom clients.** Subtypes 8 and 9 are *inside* `DATA_SUBTYPES` -- they are assigned in IEEE 802.11 Table 9-1 -- so the parser still accepts them, but on this silicon they carry a corrupt addr3. `rxinfo` does carry a CRC bit (`mac.h:54`), which `rx.py` now tests, and the filter now drops both the FCS- and PLCP-failed classes in the MAC -- so whether these frames survive at all needs re-measuring before the sink-layer gate is assumed necessary. The sink now requires a ToDS data frame's addr3 to name an AP already learned from a beacon/probe response. **FromDS frames are exempt on purpose:** their addr3 is the wired-side origin, not a claim about an AP we should have beaconed, so a hidden or briefly-missed AP still shows its clients -- an earlier unconditional version broke exactly that and `test_from_ds_client_is_receiver_not_addr3_origin` caught it.
- **WCID allocation was absent** (`TX_NO_STATION = 0xFF` hardcoded in tx.py), so PMKID, WPS and AP mode had no station slot to name. `WcidAllocator` now ports `main.c:187-204` (`mt76_wcid_alloc`) and `wcid_setup` ports `mac.c:355`. WCID 0 stays reserved for the broadcast STA (`init.c:583`), the monitor WCID stays 0xff and is never returned, and allocation stops at the kernel's `main.c:203` limit of 120 -- 128 slots exist but 120-127 are unusable. **Trap:** `mac.c:359` uses `FIELD_PREP` on `MT_WCID_ATTR_BSS_IDX`, which is `GENMASK(6, 4)`. Masking the index onto that mask instead of shifting it into the field writes 0 for every vif_idx, silently attributing every station to BSS 0. Pinned by a per-vif_idx regression test. **Unproven on air:** nothing yet calls `wcid_setup`, so this is tested register sequencing only -- validating it needs the dongle repluged.
- **Active Monitor was unimplemented.** `FAKE_MAC` inherited `UNIMPLEMENTED`, so `set_fake_mac()` returned `None` and only logged at `info`, and the UI button did nothing with no error. Now `SPOOFABLE`: `mac.c:22-24` writes MT_MAC_ADDR_DW0/DW1, and U2ME (bits 16-23 of DW1) is the autoresponder enable, so the chip HW-ACKs whatever MAC is programmed there. U2ME stays 0xff on exit as well -- mac.c arms it in `mt7601u_set_macaddr`, the only place this silicon ever gets it, so the monitor baseline already has it set. **Two traps found on the dongle:** (a) `vendor_single_wr` splits a 32-bit write across `offset` and `offset + 2`, so the U2ME mask is written to `0x100e`, which the chip does not answer reads on (times out) -- reading DW1 at `0x100c` returns only the low half, so a readback of `u2me=0x00` is a measurement artifact, not evidence the mask failed; (b) the write is faithful to usb.c:181, which does the same split. Registers verified written and restored on hardware (`DW0=0xefbeadde` after arming, `restored=True` after exit).
- **TX ACKs were never tapped, so every deauth tally read 0/N.** `driver.py:_dispatch` went straight to `iter_frames` -> parse, with no 10-byte `FC=0xD4` branch; 25 of 26 drivers have one. `record_ack` no-ops unless armed and RA is a MAC we injected as, so `_ack_counts` stayed empty, `acks_seen()` was always 0, and `deauth_client` reported `client_acks=0` while hardcoding `measured=True` -- the UI showed "0 acks" for frames that were fine. The tap now sits on the raw bytes (the parser drops control frames) and `_dispatch` no longer early-returns when only the tally is armed. A control-frame ACK is 10 bytes: FC(2) + Duration(2) + RA(6), so RA is `[4:10]`. **Proven on the air:** with `wlan1` on hostapd as AP `4a:ca:07:53:33:98`, one empty-SNAP ToDS data frame from `20:e2:17:0b:48:00` tallied `acks_seen=1` 100 ms after `inject_frame` returned True, with RX still draining beacons afterwards. Note a bare 3-address data header is 22 bytes but `_hdrlen` demands 24, so an injected data frame without its 4-byte LLC/SNAP is refused as too short -- that rejection is correct.
- **`TxQueue.used` is safe as written; do not "fix" it.** The port retires a ring slot in `collect_status`, and the status FIFO returns far fewer entries than frames submitted (measured 10 per 74), which *looks* like a permanent wedge at `entries=64`. It is not: `bulk_out_tx` is synchronous, so a transfer has completed by the time `submit` returns and `used` back to 0 is correct. The kernel's `q->used` is released in the async USB completion callback, which this port does not have. Rejected alternative: moving `pump(1)` into `submit` breaks 7 tests that assert the ENOSPC refusal path, which is unreachable while the transport is synchronous.
- **EvilTwin raised `EmptySelectError` instead of declining.** `eviltwin_modal.py` builds `Select([...], allow_blank=False)` from the host list, so an empty list crashed at compose. `_start_eviltwin` gated only on `array.members`, never on hosts, leaving the button live but the campaign unstartable. It now refuses up front with a message naming the reason. Same crash existed on `rt2500usb` (`FAKE_MAC=NONE`).
- **Live TX has not been confirmed on the air.** The injected descriptor matches capture-6's kernel reference and no probe request has been answered by an AP on the air. `inject_frame` returning True only ever meant the bulk OUT did not time out. **Do not cite TX status as evidence of emission** -- see the two corrections below; it is a free-running counter, and the "30/30 SUCCESS" figures recorded earlier were ~4 real entries, not 30.
  - **Frames were going out on the wrong endpoint, now fixed.** `tx.c` derives the pipe rather than naming it: `q2hwq(qid) = qid ^ 3`, so an unclassified injected skb (`qid=0`) becomes `hw_q=3`; `q2ep(3) = 4`; `out_eps[4]` is **0x07**. The port sent on `out_eps[2]` = 0x05 because `usb.h` names that index `MT_EP_OUT_AC_BE`. The label is a trap: index 2 carries `qid=1`, and endpoint indices come from the interface descriptor in descriptor order (`0x08, 0x04, 0x05, 0x06, 0x07, 0x09`), not ascending. `TX_QUEUE_INJECT` now names the derived index.
  - **`MT_TXD_PKT_INFO_QSEL` is 2 bits (`GENMASK(26,25)`) and was fed the endpoint index.** `dma.c ep2dmaq` returns only `MT_QSEL_MGMT` (endpoint 5) or `MT_QSEL_EDCA` (everything else). Index 2 coincidentally equals `MT_QSEL_EDCA`, which is why the field looked correct; at index 4 it would have truncated to MGMT. Now derived by `dma_queue_for_endpoint`.
  - The earlier conclusion that "injection permanently kills RX" was **wrong**, and the evidence for it was a bug in the test harness rather than in the driver: `PHASE = "probe"` was assigned inside `async def main()`, binding a function-local, while the frame callback read the module global and therefore stayed in its first phase forever. Every "0 frames during TX" reading was a structurally guaranteed zero. Measured once fixed: 251 frames during TX and 173 after, and a 45 s no-TX control holds a steady ~18/s with zero drops. Do not re-investigate RX.
  - Still unverified on the air: the endpoint fix is derived from `tx.c`, not yet measured. If directed probes still go unanswered, bisect the endpoint directly.
  - Ruled out by measurement, so do not re-investigate: wrong channel (observer swept all 14 channels, zero hits), wrong rate **only across CCK** (the sweep passed rate 0-7 into a rate_ctl whose PHY_MODE field is 0 = MT_PHY_TYPE_CCK, and `mac.c:415` WARNs on a CCK index above 3, so 4-7 were invalid CCK rather than other rates; no OFDM or HT rate has ever been put on the air), missing register write (bring-up register sets diffed; `MT_TX_BAND_CFG` already reads `MT_TX_BAND_CFG_2G`). The remaining suspect is PHY/RF calibration state below the MAC — BBP TX entries or PA calibration.
  - **The monitor WCID is valid — the chip echoes it back.** `MT_TX_STAT_FIFO` reports `wcid=0xff`, matching the `mon_wcid->idx` the descriptor carries, so WCID 0xff resolves in hardware and no "fake monitor WCID" fallback is needed. Do not go looking for one.
  - **RF emission is armed; power-on TX was ruled out by measurement.** After a normal `connect()`: `MT_MAC_SYS_CTRL=0x0c` (`ENABLE_TX|ENABLE_RX`, matching `init.c:248`), `MT_MAC_STATUS=0` idle, `MT_TX_BAND_CFG=0x4`, `RF_PA_MODE_CFG0=0x010055ff`, `TX_ALC_CFG_1=0xc954000a` (temp-comp field set by `set_initial_tssi`), `RF_SETTING_0`/`RF_BYPASS_0=0` (RF enabled, not bypassed). Sampling `MT_MAC_STATUS_TX` across 20 injected frames never observes it set, but a 20 ms poll cannot resolve a per-frame window, so that is not evidence of a stalled TX engine on its own.
  - **`BBP1` reads `dac_field=0`, which is correct.** `mt7601u_set_tx_dac` is a `dev_dbg`-only hook in the kernel and is never called on the TX path, so power-on 0 is the expected value. Not a defect.
  - **The out-of-tree driver that advertises working injection has no injection changes.** `Aexe-Software/MT7601U-Driver-Linux` is upstream v7.2 plus AP beaconing: its `dma.c`, `phy.c`, `initvals.h` and `initvals_phy.h` are byte-identical to upstream, and its `mt7601u_tx()` WCID selection is upstream's `mon_wcid`/`sta`/`group_wcid` chain verbatim. Its README's "fallback in `mt7601u_tx()` that supplies a fake monitor WCID" does not exist anywhere in that tree. Do not re-investigate this lead.
  - **CONFIRMED on hardware, 2026-10-03: this silicon transmits injected frames fine, so the fault is in this port's TX path.** Built the out-of-tree driver from source against this kernel (needs `BUILD_CC=clang LD=ld.lld`; CachyOS kernels are clang-built, and `mt7601u_config`/`mt7601u_set_rts_threshold` need the post-6.x `int radio_idx` parameter or clang 23 errors out). Installed it, blacklisted the in-tree module, put a dongle in monitor mode and ran `aireplay-ng -9`:
    ```
    16:27:14  Injection is working!
    16:27:16  82:A4:FA:2B:44:AB - channel: 6 - 'Flybox_442B'   27/30:  90%
    16:27:18  40:ED:00:C2:55:E8 - channel: 7 - 'TT_55E8'      28/30:  93%
    ```
    55 directed probe responses from two live APs. Reproduced on a second run at 24/30. The RF chain, EEPROM power tables, PA calibration and `mon_wcid` 0xff are all therefore correct on this hardware. Everything already ruled out above (endpoint, QSEL, WCID, channel, rate, register writes, calibration, RF arming) describes state the kernel also relies on, so those explanations cannot be why this port goes unanswered.
  - **The kernel's success path was verified, not assumed: the AP answers the spoofed Addr2, not the card.** A tcpdump on the second dongle during `aireplay-ng -9` caught Probe Responses addressed to `0a:73:0a:25:07:d3` -- aireplay-ng's injected source, neither dongle's MAC. So any campaign that spoofs Addr2 (`AutoDeauth` does by design) is the correct like-for-like comparison, and a "no reply to our own MAC" result cannot be blamed on the address used.
  - **Every host-observable layer of this port's TX matches the kernel, and it still does not reach the air.** Traced live with the port's own transport: 84-byte descriptor written to endpoint **0x7**, 84 bytes accepted. Decoded field by field against `struct mt76_txwi`: `flags=0`, `rate_ctl=0x0000` (CCK 1 Mbps, matching the kernel's on-air `1.0 Mb/s 11b`), `ack_ctl=0`, `wcid=0xff`, `len_ctl=0x1035` (53-byte frame, pktid 1), `ctl=0`; DMA info `0x0508004c` = LEN 76 on an 84-byte transfer, D_PORT 0, TYPE 0, 80211+WIV set, QSEL 2. **Re-derived capture-6 from its raw usbmon bytes to check this rather than trusting the earlier decode:** the reference info word is `30 00 08 05` = little-endian `0x05080030`, LEN 48, so it is the *same shape* as ours, not the `30000805` the previous entry quoted. Its txwi is `0000000000ff1a10000000000000000000000000` — `rate_ctl=0x0000`, identical to ours. So both remaining candidates from the previous version of this entry are **closed**: (a) the WMM/TXOP registers are a dead end, and (b) the kernel resolves monitor rate from `wcid->tx_rate`, which is 0 for `mon_wcid`, so it writes the same `rate_ctl=0` this port does.
  - **TXOP/EDCA is not the cause. Measured, not assumed.** Programmed the kernel's own `mt7601u_conf_tx` values in phases and counted frames the second dongle heard: `MT_WMM_TXOP(3)` set to 3008 us and `MT_EDCA_CFG_AC(3)` set to `0x000000c0`, so TX airtime is unambiguously granted on the inject queue `hw_q = q2hwq(0) = 3`. Result: 0 of 40 injected probes on the air per phase, across baseline, TXOP-only, full `conf_tx`, and all-four-queues-programmed. Do not re-investigate.
  - **The chip is genuinely modulating: `MT_MAC_STATUS_TX` does go high.** The old 20 ms poll could not resolve a per-frame window, so it was never evidence either way. Injecting back-to-back with no inter-frame gap and polling in a tight loop sees TX_BUSY high in **459 of 8772 polls (5.2%)** across 74 frames. This is a working TX engine, so do not re-investigate "the MAC never starts".
  - **The frame does not leave the antenna, measured below the 802.11 parser.** Every earlier count only tallied frames `parse_80211_frame` successfully returned, and `driver.py:_handle_rx` drops anything the parser rejects -- so a frame that reached the air but failed to decode would have scored exactly 0, indistinguishable from never being transmitted. Tapping the parser's raw input instead, across a no-injection baseline, an injection window and a following idle window: **123 frames received during injection, 0 of them contain the transmitting dongle's own MAC.** The witness is sound in the same run: the grep finds MACs in raw bytes (it matched another device's probe requests), and 4 baseline frames carried an unrelated address. So the port's RX genuinely hears the channel, and the absence is real.
  - **`0a:73:0a:25:07:d3` is another device on this network, not a stale kernel session.** The address aireplay-ng randomly picked and reused is actively transmitting probe requests (`a1=ff:ff:ff:ff:ff:ff a2=0a:73:0a:25:07:d3`, rssi -83/-85) from an unrelated source. Any test grepping for it as evidence of our own emission, or of a leftover kernel driver, is reading ambient traffic.
  - **capture-6 contains two descriptor variants, and the port can only build one.** `scripts/chips/mt7601u/verify_tx.py` parses all 8135 recorded bulk OUTs and finds 7680 of one form and 455 of another:
  ```
  x7680  info 30000805  txwi 0000000000ff1a10...  wcid=0xff ack_ctl=0x00 byte_cnt=26
  x455   info f4000805  txwi 00000000027edf10...  wcid=0x7e ack_ctl=0x02 byte_cnt=223
  ```
  Both agree on `QSEL=2`, `D_PORT=0`, `TYPE=0`, `80211`, `WIV`, `rate_ctl=0x0000`, and both sit on endpoint 0x07 — the difference is **which WCID and whether the chip stamps the sequence number**. `MT_TXWI_ACK_CTL_REQ` is `BIT(0)` and `MT_TXWI_ACK_CTL_NSEQ` is `BIT(1)`, so `ack_ctl=0x02` is NSEQ, **not** a link-layer ACK request; do not read it as one. The 455-frame variant carries `wcid=0x7e` (126), a WCID inside the 128 the port clears, and it came from the interface that also did 2149 MCU inband writes — the one actually being driven.
  - **This is the strongest remaining lead, and it is a known unported gap.** `tx.py:TX_NO_STATION = 0xFF` is hardcoded on the reasoning that `init.c:590` gives monitor injection `mon_wcid->idx = 0xff`. That is right for a pure monitor interface, but capture-6 proves this driver also transmits on a genuinely allocated WCID. `wcid.py` clears all 128 slots and never allocates one — no `wcid_mask` bookkeeping equivalent to `main.c:191`, and no `mt7601u_mac_wcid_setup`, so WCID 126's `MT_WCID_ADDR` entry holds `WCID_ADDR_INVALID` and the MAC has no station entry to rate-match against. The port literally cannot emit a descriptor in the form that reaches the air.
  - Settle it with WCID allocation ported and a descriptor built on the allocated WCID, then re-run the over-air count below the parser. Until then do not claim TX works, and do not claim the descriptor is the fault — `verify_tx.py` proves the `wcid=0xff` form matches the kernel exactly.
- **TX now has a verify gate.** `scripts/chips/mt7601u/verify_tx.py` replays capture-6's recorded descriptors, decodes both sides against `struct mt76_txwi`, and asserts field-for-field equality — the stage that was previously only compared by eye, which is how the live-TX defect survived this long. It reports PASS on the `wcid=0xff` variant and names the WCID gap. Note the capture is truncated at 32 bytes per record, so only the info word and txwi are checked; the frame body is not recorded.
- Register-write captures must parse both vendor-request encodings. The kernel writes registers as `bm=0xc0 br=0x07 wIndex=reg wLength=4` with the value in the data stage; this port writes `bm=0x40 br=0x02 wIndex=reg wLength=0` with the value in `wValue`. Diffing with only one form reports the other side as silent.
- **The TX status FIFO is drained on every submit, but it cannot prove emission.** `dma.c:280` `mt7601u_tx_tasklet` queues `stat_work` 10 ms after every TX to fetch `MT_TX_STAT_FIFO`; `tx_status.py` ports the fetch (`mac.c:157`) and `tx_ring.py:submit` drains inline, folding each popped status into a ring-slot release. The kernel defers because entries arrive asynchronously; draining inline is the tightest approximation and needs no timer, at the cost of missing an entry that has not landed yet — the next submit picks it up. `driver.tx_statuses()` returns the recent window.
  - **Measured: the register is a free-running counter, so most "success" readings are noise.** Read 8 times with nothing in flight and it returns `0xff23, 0xff22, 0xff22, ...` -- it decrements every read whether or not a frame was sent. `fetch()` is self-consistent with `mac.c` (`valid = !!(val & BIT(0))`), but that means a VALID word only appears on a counter wrap, not per frame. 74 injected frames yielded **10** statuses, not 74. Every earlier figure in this document ("30/30", "24/30", "measured 30/30") counted ~4 real entries and overstated the evidence. **Do not treat TX status as a transmission indicator.**
- **The kernel driver is a valid comparison oracle.** `/lib/modules` may lack a tree for the running kernel after a package upgrade, but when it loads it receives normally and its usbmon capture is the reference for bring-up.

- **The RX filter's polarity is settled, from the C, without the dongle.** `main.c:116` is `MT76_FILTER(OTHER_BSS, MT_RX_FILTR_CFG_PROMISC)`, and `main.c:107` expands to `rxfilter |= !(flags & FIF_OTHER_BSS) * bit` -- the bit is set when mac80211 did **not** ask for other-BSS frames. So `PROMISC` set means *drop what is not addressed to us*, and a monitor clears it. The capture agrees: `0x00017f97` at `init.c:245`, then `0x00001093` with bit 2 clear. `verify_pcap` still waives the substitution, because this port writes the monitor value where `mac_start` writes the managed default.
- **Temperature compensation never refreshes after boot.** `phy.c:530 mt7601u_read_temp` (declared `s8`) is unported, and nothing schedules `main.c:22-25`'s `mac_work`/`cal_work` at `MT_CALIBRATE_INTERVAL` (`constants.py:553`, defined and unused). `cal.py:223` recomputes `curr_temp` from `phy.raw_temp`, but `raw_temp` is only ever set once by `read_bootup_temp`, so the DPD and PLL-protect branches in `temp_comp` can never fire again. Long-run TSSI and temperature drift are uncompensated.
- **Teardown is ported.** `init.py:mac_stop_hw` is `init.c:257`: the beacon-timer clear, the TX/RX DMA-busy polls, the 200x TxQ page-count drain (`init.c:272-276`) and the RxQ drain (`init.c:285-296`, seven consecutive clean reads because `init.c:292`'s `ok++ > 5` tests the pre-increment value). Every poll there only warns in the C and only warns here. `driver.py:close()` runs it **before** stopping the reader, because the RxQ drain only empties while the host is still consuming bulk-IN. `init.c:273-275` reads three registers `regs.h` does not name; they are `constants.py:MT_PCNT_0438/0A30/0A34`. `mcu.c:531 mcu_cmd_deinit` has **no wire counterpart to port** -- it is `usb_kill_urb` plus a buffer free, and this port reads MCU responses synchronously, so there is no URB to kill. Same for `dma.c:541 dma_cleanup`: host-side only.
- **A failed bring-up powers the chip down.** `init.c:413-423` unwinds through `err_rx -> err_mcu -> err` on every failure, and `chip_onoff(false)` is the only step of that with wire effect. `_bringup` is now a try/except around `_init_hardware` that runs it and stops the RX reader (`init.c:414 dma_cleanup`) before re-raising; without it a failure midway left the chip powered with `WLAN_EN` set and DMA armed.
- **The poll helpers reproduce the C's read counts.** `init.py:poll` / `poll_msec` are `core.c:28` / `core.c:50`: `timeout // 10 + 1` reads, because `core.c:33` divides and `core.c:43` tests the counter after the read. `poll_dma_idle(50)` now issues the C's six reads, not one, and `poll_mac_idle` eleven, not a hundred. **`poll` adds no delay between reads, deliberately:** `core.c:42` is `udelay(10)`, one vendor-request read is a USB round-trip longer than that, and `time.sleep` cannot deliver 10us on Windows -- at the 20001 iterations `init.c:234` budgets, its ~0.5ms floor turned a 200ms poll into ten seconds of test time. `poll_msec` keeps its 10ms, which is past the transfer cost.
- **`is_valid_ether_addr` is only half ported.** `mac.c:15-20` rejects an EEPROM MAC that is all-zero, all-ones **or multicast** (bit 0 of byte 0), and installs `eth_random_addr()` on failure. `eeprom.py:143-145` tests only all-zero and all-ff, and `eeprom.py:234` installs all zeros instead of a random address. An EEPROM holding `01:...` passes here and is replaced upstream.
- **`is_warm` reflects the branch actually taken.** `load_firmware` returns True when `mcu.c:416 firmware_running` found `MT_MCU_COM_REG0 == 1` and skipped the download, and `driver.py` assigns `is_warm` from it.
- **`SUPPORTED_CHANNELS` is 1-14 by decision, not by oversight -- do not gate it on the EEPROM.** `init.c:565-571` derives the kernel's advertised 2.4 GHz list from `MT_EE_COUNTRY_REGION` via `ee->reg`, and `eeprom.py:286-314` computes `ee.reg` faithfully but nothing reads it. That is deliberate: wifit3 ships channel 14 for the regions that use it, and a region-gated list would silently drop it. The channel-14 path itself **is** verified faithful: `phy.py:apply_ch14_fixup` matches `phy.c:322` on both branches (the BBP 4/178 writes and the `real_cck_bw20 - 2` CCK adjustment, clamped by `_s6` where the C relies on `s8` truncation), and `FREQ_PLAN` carries all 14 entries.

## Driver Entry Points

- Bring-up order: `driver.py:connect` (kernel-driver refusal, interface claim, pipe map, liveness probe -- none of it part of the kernel's register sequence) → `driver.py:_bringup` → `init.py` (`chip_onoff`, `wait_asic_ready`, `reset_csr_bbp`, `init_usb_dma`, `mcu_cmd_init`, **RX arming**, `write_mac_initvals`, `init_bbp`, `mac_start`). `verify_pcap` drives `_bringup` directly.
- Injection descriptor: `_inject_frame` → `tx_ring.py:submit(ack=False)` → `tx.py:build_tx_dma`. The `ack=False` is load-bearing: `MT_TXWI_ACK_CTL_REQ` makes the chip expect an ACK to a frame whose Addr2 is spoofed, which can never be matched, and it reported `SUCCESS=0` for 15/15 frames where `ack=False` reported 15/15.
- TX status: `tx_status.py` — `TxStatusFifo.fetch`/`drain` read-pop `MT_TX_STAT_FIFO` one entry per transmit. Drained automatically on every submit; `driver.tx_statuses()` returns the recent window.
- EEPROM decode: `eeprom.py` — `MT7601UEeprom.read`, `set_macaddr`.
- Firmware download: `firmware.py`, `mcu.py:MT7601UMcu.upload_firmware` (`mcu.c:356`). Reads `/usr/lib/firmware/mediatek/mt7601u.bin.zst`; the blob is not bundled into the PyInstaller build.
- MCU inband commands: `mcu.py` — `msg_send`, `calibrate`, `write_reg_pairs`, `burst_write_regs`. EP 0x8 out, 0x85 in.
- Channel tune: `phy.py:set_channel` → `rf_wr`, `set_bw_filter`, RF tables generated by `scripts/chips/mt7601u/gen_initvals.py`.
- Calibration: `cal.py:init_cal` (`phy.c:1122`).
- TX descriptor: `tx.py:build_tx_dma`, `build_txwi`; URB bookkeeping in `tx_ring.py`. Endpoint selection: `tx.py:TX_QUEUE_INJECT` (the index `tx.c` derives) and `dma_queue_for_endpoint` (QSEL).
- RX decode: `rx.py:iter_frames`, `decode_segment`, `get_rssi`.
- USB pipes: `transport.py:assign_pipes`, `bulk_in_rx`, `bulk_out`, `vendor_request`.

## Debug log

- **2026-10-02 — usbmon text field order.** Cost three wrong conclusions in one investigation, two of them fabricated leads. Check any usbmon field against the C before trusting a diff: the value half is the first hex group, the register is the second, and every 32-bit write arrives as two 16-bit requests.
- **2026-10-02 — `tshark` cannot write captures on this host.** AppArmor denies every output path including `/tmp/opencode`. usbmon text is the only usable source, which is why the field order above matters.
- **2026-10-02 — usbmon stops producing output after `modprobe -r mt7601u`.** It returns zero lines for *all* traffic, including a full connect. `modprobe -r usbmon && modprobe usbmon` restores it. Always confirm a capture is non-empty before analysing it.
- **2026-10-02 — silent-zero failures are indistinguishable.** RX returning nothing looks identical whether the cause is URB count, arming time, register values or endpoint mismatch. The only thing that resolved it was exhausting the list; record what has been ruled out before forming the next hypothesis.
- **2026-10-03 — a vendor README is not a diff.** The out-of-tree driver claiming 30/30 injection turned out to be upstream plus AP beaconing, with the advertised monitor-WCID fallback absent from its source. Read the code it ships, not the claims in its README.
- **2026-10-03 — count received bytes, not parsed packets.** `_handle_rx` drops any frame the parser rejects, so "we heard 0 of ours" was equally consistent with "our frame reached the air and failed to decode". Every TX conclusion in this file rested on that blind spot. Wrap `parser.parse_80211_frame` and grep its raw input instead, and keep a no-injection baseline window to separate your own traffic from ambient.
- **2026-10-03 — a zero must be shown to be a zero.** Two of the strongest-sounding numbers in this investigation were wrong on inspection: `MT_TX_STAT_FIFO` "SUCCESS 30/30" was ~4 entries against a free-running counter, and capture-6's reference info word was quoted as `30000805` when the raw bytes decode to `0x05080030`. Re-derive a claim from the bytes before building on it.- **2026-10-04 — CORRECTION: this port's TX does reach the air. The "does not leave the antenna" conclusions above were a harness bug.** With both dongles freed from the kernel driver and driven by this port (`rmmod` of the blacklisted module, not `modprobe -r`, which reports "Module not found" because the blacklist makes modprobe skip the name), dongle B injected 5 probe requests carrying a unique source `de:5c:00:01:11:22` and **all 5 appeared in dongle A's raw RX**. The zero in the earlier entries is the `PHASE` closure bug described above, reproduced a second time: the first attempt hooked `_read_once` *after* `connect()` had already started the reader thread, so the tap was never called and "0 raw buffers" was a guaranteed zero while RX was demonstrably live (33 decoded packets in the same window). Hook the tap before `connect()`, and assert the tap is live (nonzero buffers in a no-injection window) before believing any absence. Do not re-investigate the TX path.
- **2026-10-04 — Active Monitor proven over the air, two dongles.** With A armed via `enter_active_monitor(b_mac)` and B transmitting a ToDS null-data frame addressed to that MAC, **B counted `acks_seen` delta = 1** for the ACK that A's autoresponder emitted off the air, with `TX_STAT_FIFO` reporting `success=True` on the same frame. A frame addressed to A's *real* MAC was not ACKed (`delta = 0`), which is correct: the autoresponder only answers for the MAC programmed into DW0/DW1. `wcid=0xff` on these frames is the monitor WCID echoing back as expected, not a fault. The mechanism the user reported as "not implemented for mt7601u" works end to end on real silicon.
- **2026-10-04 — the ACK round-trip is ~57ms here, so the inherited 20ms `MAX_ACK_DELAY` made every ACK-measured send report a miss.** Feature-parity audit against the other drivers found MT7601U was the only chip that never overrode `MAX_ACK_DELAY`. Measured on two dongles, ch6, A armed via `enter_active_monitor(b_mac)` and B injecting the matching ToDS frame, tally polled every 1ms: min 2.1ms, median 57.3ms, p90 72.6ms, max 119.8ms -- **14 of 15 trials landed outside the 0.02 window**. Ruled out USB bulk aggregation as the cause before touching a register: clearing `MT_USB_DMA_CFG_RX_BULK_AGG_EN` moved the median only 60.1ms -> 61.2ms, so the latency is this chip's bulk-RX scheduling, not a knob. Overrode `MAX_ACK_DELAY = 0.25`. Verified both directions on hardware: `send_until_ack` returned True for 10/10 genuinely-ACKed frames with 0 false positives, and returned False for 8/8 frames sent to a MAC that was not armed, so the wider window waits longer without inventing successes. This was the "deauth doesn't work" symptom, and it was a base-class constant that suited other chips, not a fault in the port.
- **2026-10-04 — audit note: `RX_BULK_AGG` latency is a dead end here.** Recorded because the register looks like the obvious culprit and the A/B above already paid for the experiment. If a future change reopens the question, the number is in this entry; do not re-run it.
- **2026-10-06 — `is_kernel_driver_active` is Linux-only, and its failure was reported as a missing WinUSB driver.** Windows libusb raises `NotImplementedError` from it. `transport.py:claim` and `driver.py:_refuse_kernel_bound_chip` both called it unguarded; `wlan/interface.py:94` catches `NotImplementedError`, classifies it as a permissions fault, and `device/manager.py:433` then offers a WinUSB install. Net effect: the card could never connect on Windows, and the symptom was a "WinUSB needs to be installed" modal on a card already correctly bound to WinUSB. Guarded per the pattern `mt76x0u`, `mt7925au` and `rtl8821au` already use. If that modal reappears on a bound card, suspect a connect-time exception being reclassified, not the installer.
- **2026-10-06 — hardware confirms the descriptor endpoint order.** Read off `148f:7601`: `in_eps 0x84,0x85`, `out_eps 0x08,0x04,0x05,0x06,0x07,0x09`, `in_max_packet 512`, `MT_ASIC_VERSION 0x76010001`, `MT_MAC_CSR0 0x76010500`, `MT_EFUSE_CTRL 0x80008800`. So `out_eps[0]` is 0x08 (inband command) and `out_eps[4]` is 0x07 (injection), matching both the capture and the `tx.c` derivation, and the `usb.c:299` revision gate passes on silicon.

## Audited against the C, subsystem by subsystem

`eeprom.py`, `phy.py`/`cal.py`/`initvals_phy.py`, `tx.py`/`tx_ring.py`/`tx_status.py` and
`rx.py`/`wcid.py` have each been read line-against-line with the matching v6.19 `.c`. The point
of the exercise was the one failure mode a capture and this hardware cannot catch: a literal in
the Python where the C computes a value, correct on these two dongles and wrong on a third.

### Fixed, each from the C

- **The AGC was pinned to an initvals literal.** `phy.c:948 agc_default` is
  `(lna_gain - 8) * 2 + 0x34` and `phy.c:434` calls `agc_reset` on every scan hop. None of
  `agc_default`/`reset`/`save`/`restore` was ported, so BBP 66 kept `0x14` from
  `initvals.h:34`. Recoverable from the captures via the `0x37 - lna_gain` write: the superwang
  computes `0x34`, the antenna `0x24`. **Neither is `0x14`** -- the literal was wrong on both
  dongles, which is this audit's whole thesis. `driver.py:set_channel` now maps the `scan` flag
  onto `main.c:271`/`:281`'s `sw_scan_start`/`sw_scan_complete` bracket, which is the only
  signal the Driver ABC carries for them.
- **`int_to_s6` saturates; two call sites were wrapping.** `eeprom.h:133` clamps to `0x20`/`0x1f`
  before masking. `phy.py` had a second, unclamped `_s6` (`-34` became `+30`, inverting channel
  14's CCK power) and `cal.py:_set_initial_tssi` dropped the call entirely (`-186` became `+6`,
  38 steps the wrong way on the TX ALC temperature compensation). Both now use the faithful
  `eeprom.py:int_to_s6`. Unreachable on these dongles: both read TSSI slope 0, and both CCK
  bw20 values are in range -- exactly why it went unnoticed.
- **The four TSSI gain readings are `s8`.** `phy.c:645` declares `s8 res[4]`; `bbp_rr` returns an
  unsigned byte, and the two differ by 256 for any reading at or above `0x80`. The superwang's
  recorded `res[0]` is `0xff`, so this was already wrong in memory on that unit.
- **Sequence numbers are stamped in software.** See the `MT_TXWI_ACK_CTL_NSEQ` entry above.
- **An ACK is requested per destination, not per session flag.** `tx.c:158` sets
  `MT_TXWI_ACK_CTL_REQ` only when `IEEE80211_TX_CTL_NO_ACK` is clear, which mac80211 sets for a
  group addr1. `build_tx_dma` now vetoes the request when addr1 is a group address: a broadcast
  deauth injected with the ACK tally armed was asking the MAC to wait out its retry budget on an
  ACK that can never arrive. The remaining deviation is deliberate: a unicast frame with the
  tally disarmed still clears REQ, where the C would set it.
- **`RATE_CONTROLLED` was emitting MCS 127.** `0xFF & MT_TXWI_RATE_MCS` is `0x7F`, not a
  sentinel. `tx.c:151` resolves `rate->idx < 0` to `wcid->tx_rate`, which for the monitor WCID is
  0, and `tx.c:183` derives the packet id from `rate_ctl & 0x7` rather than substituting 0.
  `MT_TXWI_RATE_MCS` is also `GENMASK(6, 0)`; the 3-bit bound belongs to the pktid encoder, and
  the validator had conflated the two.
- **The RX segment floor was 32 where the C's is 40.** `dma.c:119` computes one `min_seg_len` and
  `dma.c:123`/`:127` both use it; the port had the first right and substituted `RXWI_LEN + 4` for
  the second. A `dma_len` of 32 or 36 made the C abandon the whole chained buffer and the port
  keep walking it. `rx.py:MIN_SEGMENT_LEN` was already 40 and simply unused there.
- **`MT_WCID_DROP` was never written.** `main.c:229` clearing it on station add is the only place
  in the entire driver that touches it, so the power-on value is load-bearing: a slot whose bit
  came up set has its traffic discarded by the MAC with nothing to show why. `wcid.py:sta_add` /
  `sta_remove` now port `main.c:220-252` whole -- the drop bit, `set_ampdu_factor` (`mac.c:371`),
  and the `vif_idx = 0` that `main.c:251` forces on release so the attr word is zeroed rather
  than left naming the old BSS.
- **Endpoint 0 is refused for frames.** `dma.c:355 q2ep` returns `qid + 1`, so a frame endpoint is
  never 0; index 0 is the MCU inband command pipe, and frame bytes on it stop the receive stream
  (`transport.py` already records that hazard). `dma_queue_for_endpoint` still answers for 0,
  because `ep2dmaq` does.

### Recorded, not fixed -- unreachable here, or needing a decision

- `eeprom.py:rf_freq_off` is not truncated to `u8` (`eeprom.h:95`), so it can go negative or past
  255 where the C wraps. Masked today: its only consumer pushes it through an 8-bit field. It
  becomes live the moment `__mt7601u_phy_freq_cal` is ported, because `phy.c:1057`/`:1062`
  compare the value.
- `rx.py` drops a non-packet FCE type where `dma.c:102` only `dev_err_once`es and delivers the
  segment. Kept as a drop because there is no mac80211 downstream to discard it; the comment no
  longer claims the C drops it.
- `mt76_mac_process_rate` (`mac.c:396`) is unported, so `RxFrame.rate` is the raw rxwi word --
  which is what the C passes to `phy_get_rssi` too, so the name is right. Nothing consumes it;
  CCK/OFDM/HT, short preamble, SGI and STBC are all undecoded.
- `MT_RXINFO_DECRYPT` / `PN_LEN` (`mac.c:473-484`) translate into mac80211 `RX_FLAG_*_STRIPPED`
  bits. Unreachable: hardware decryption needs the key table, which is unported.
- The `rxwi->zero[]` sanity check (`dma.c:97`) and the `MT7601U_STATE_INITIALIZED` gate
  (`dma.c:142`) have no counterpart. Both are diagnostics or guards with no delivery effect here.
- With `MT_RXINFO_L2PAD` set and `MPDU_LEN` exactly equal to the payload length, the C over-reads
  two bytes of the FCE trailer and the port's slice clamps two bytes short. The port's behaviour
  is the better one; the hardware's two pad bytes make the case nearly unreachable.
- `set_channel` derives `chan_ext_below` from the bandwidth (`phy.py`), collapsing
  `NL80211_CHAN_HT40MINUS` and `HT40PLUS` (`phy.c:381`). Unreachable: 20 MHz only.
- `phy.c:1180 bbp_set_bw`'s bandwidth-change path and `phy.c:289 load_bbp_temp_table_bw` are
  unported, as is `phy.c:1252 prev_pwr_diff = 100` and `phy.c:437 dev->chandef`. All consumers
  are in the unported TSSI/frequency-calibration runtime loop.
- `set_rx_path` / `set_tx_dac` add a `& 0x3` the C does not have (`phy.c:1213`, `:1223`).
  Unreachable: `init.c:404-405` passes 0 to both.
- `wcid.py:WcidAllocator` refuses cleanly where `main.c:197-203` sets the mask bit before the
  `> 119` test and permanently burns it. The port's version is the better one. `GROUP_WCID(0)`
  = 126 (`mt7601u.h:106`) is still neither reserved nor obtainable, which is harmless only
  because the limit stops at 119.
- `mcu.c:514-528`'s persistent response IN URB on `MT_EP_IN_CMD_RESP` stays unported: this port
  reads each command's response synchronously. No wire difference, and it is what makes
  `mcu_cmd_deinit` a no-op here.
- `mt76_mac_set_ampdu_factor` is wired into `sta_add`/`sta_remove` but nothing calls those yet,
  so `MT_MAX_LEN_CFG` still holds the `initvals_mac.py` value rather than `0xa3fff`.

`initvals_phy.py` was checked entry by entry against `initvals_phy.h` -- all twelve tables match
in length, content and order, including the deliberate RF 0:12 omission and the `rf_vga` 36-40
and `rf_channel` 50-53 gaps. `eeprom.py` was additionally driven against a Python
re-implementation of `eeprom.c` over 4,000 synthetic EEPROMs; every decoded field matched except
`rf_freq_off` above.
